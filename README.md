# Notes LocalStack Infra

This repository contains the infrastructure layer for the notes platform: Terraform, LocalStack, PostgreSQL, and the Lambda ZIP artifact dependency generated by the backend project.

## Overview

The purpose of this repository is to simulate a cloud-like environment locally and in CI/CD without depending on real cloud services. It brings together the database, AWS-compatible resources, and the Lambda packaging flow required by the backend application.

## Tech Stack

- Docker
- Docker Compose
- LocalStack
- Terraform
- PostgreSQL
- GitHub Actions
- AWS service emulation
- Lambda packaging workflow
- Secrets management through local files and CI secrets

## Requirements

- Docker Desktop or Docker Engine
- Terraform
- Access to GitHub Actions for the infrastructure repository
- WSL or a Linux shell for some Lambda packaging tasks

## Local Setup

### 1. Create local secret files

Use the example files as templates and create the real values locally:

- .env
- infra/terraform.tfvars

### 2. Start the local services

```bash
docker compose down
docker compose up -d
```

### 3. Apply Terraform

```bash
cd infra
terraform init
terraform plan
```

Important: for local development, you must pass 2 variables explicitly to apply Terraform:

1. The path to the generated artifact in the backend repository
2. The processor architecture (arm64/x64)

```bash
terraform apply \
  -var="lambda_zip_path=/absolute/path/sqs-consumer.zip" \
  -var="lambda_architecture=x86_64"
```

## Environment Files

The root .env file is used by Docker Compose, and the Terraform variables file is used by the infrastructure layer.

Example:

```env
POSTGRES_USER=admin
POSTGRES_PASSWORD=admin123
POSTGRES_DB=notesdb
```

```hcl
db_host             = "localhost"
db_port             = 5432
db_name             = "notesdb"
db_username         = "admin"
db_password         = "admin123"
lambda_architecture = "arm64"
```

## Security Note

This repository keeps local secrets outside Git using .env files and Terraform variable files. Those files are excluded from version control to avoid leaking credentials. The sensitive values shown in this README are only for lab and portfolio learning purposes.

## CI/CD Workflow

There are two GitHub Actions workflows:

- .github/workflows/terraform-localstack.yml: main workflow for deployment and validation
- .github/workflows/terraform-localstack-debug.yml: step-by-step debugging workflow

Both depend on the Lambda ZIP artifact generated by the backend repository. The expected artifact name is:

- sqs-consumer-zip

If the artifact expires (7 days), it is necessary to rerun the backend workflow before starting the infrastructure workflow again.

## LocalStack Version

The environment is explicitly pinned to:

- localstack/localstack:3.0.0

This avoids drift and licensing issues that can appear when using the latest tag in automated runners.

## Required Secrets and Variables

In GitHub Actions, these values must be configured through repository secrets or variables:

- DB_NAME
- DB_USER
- DB_PASSWORD
- BACKEND_REPOSITORY
- BACKEND_ARTIFACT_TOKEN

## Debug Flow

The debug workflow allows the process to be reviewed in stages using the DEBUG_UNTIL environment variable. This is useful for validating LocalStack, the health check, the Lambda artifact download, and the Terraform apply logic step by step.

1. checkout
2. secret validation
3. BACKEND_REPOSITORY validation
4. Lambda artifact download
5. validation of downloaded ZIP
6. Terraform setup
7. LocalStack healthcheck
8. Lambda architecture resolution
9. terraform init + terraform plan (+ apply if apply=true)

Recommended usage for debugging:

- Push with DEBUG_UNTIL="3"
- Push with DEBUG_UNTIL="5"
- Push with DEBUG_UNTIL="7"
- Push with DEBUG_UNTIL="9" and APPLY="false"
- Push with DEBUG_UNTIL="9" and APPLY="true"

It uses the Docker socket to enable Lambda creation/execution on the runner.
